# Completion tracking and SCORM 1.2

Configure lesson order, identity, branding, unlocking and package metadata in `src/data/course-config.ts`. Keep learner-facing lesson labels and copy in `src/data/course.ts`. Define the required activities in `src/data/course-completion.ts`; each one needs a unique `id`, unique DOM `targetId`, lesson `path`, label, type and explicit `required` value. `validateCourseConfig` fails the build for duplicate IDs or targets, invalid routes, malformed exploration children, invalid watch thresholds, or a storage key without the course slug and version.

The neutral example has Welcome at `/` and Practice at `/topics/practice/`. `src/pages/[...lesson].astro` generates named and nested lesson routes from the ordered configuration. Add matching page copy in `courseData.lessonPages` for each new route. There is no fixed lesson count or milestone count. The first lesson uses `/`; later lessons use trailing-slash paths. The standard footer is fixed plain text and never contributes to completion.

A one-page course instead keeps one lesson at `/` and sets `navigationMode: "sections"` with configured `navigationLessons` pointing to real anchors. Optional `sections` group milestone labels in Progress; every configured milestone must appear in one group. Section links and the Lessons menu only navigate and focus content; selecting a link grants no credit, although a destination VIEW section can qualify once genuinely visible. Multi-page courses retain route-based locking, resume and explicit packaged `index.html` links.

## Completion rules

- `view`: add matching `id` and `data-completion-id` to an ordinary content section. It completes immediately when the section enters the central viewport zone while the document is visible; no dwell timer or 900 ms delay is required. Offscreen, hidden or collapsed content and other lesson pages do not qualify. Navigation itself grants no credit, though a destination that becomes genuinely visible can satisfy VIEW. Earned completion and resume remain intact; interactions and videos keep their separate requirements.
- `watch`: add both attributes to a `<video>`. Merged unique `video.played` ranges must reach `threshold`, default `0.8`. Replays and skipped gaps do not add credit.
- `submit`: add both attributes to a form and `data-completion-option` to selectable answers. A real selection and valid submission count as an attempt, regardless of correctness. The shared single-choice `PremiumAssessment` calls `requestSubmit()` on intentional radio change, so it shows feedback and records the attempt without a separate button. `AssessmentSequence` uses the same rule for each question form, with a distinct target `${sequenceId}-${question.id}` and a distinct milestone. Its arrows only change the visible question. Initial rendering and restored selections never call `requestSubmit()`; matching still requires its explicit valid submission.
- `complete`: add `id`, `data-completion-id` and `data-completion-trigger="complete"` to the activity, then dispatch `course-progress:complete` with `{ activityId }` at the approved completion moment.
- `explore`: add both attributes and JSON `data-required-items` to the group. Dispatch `course-progress:explore` with `{ activityId, itemId }` for each configured child. Every child must be explored. `ExploreGroup.astro` demonstrates this contract. The ordered compact `StepGroup` leaves every step accessible from the start and credits each child only when its displayed panel is visible, including the initially displayed step; ordered labels and optional letters do not change the completion rule.

For any interaction with one displayed panel at a time, use `watchVisiblePanelExploration` from `src/lib/visible-panel-exploration.ts`. Pass the instance root, all panels, a getter for the currently active panel, an item-ID getter and the course UI store. Call its returned check after changing the active panel. It also checks the initial and restored panel on viewport entry, document visibility changes, and ancestor reveal or transition changes. The helper checks the panel and ancestors against the same rendered-visibility rules as VIEW, plus viewport intersection. Only the active panel can dispatch EXPLORE; the progress manager confirms required item IDs, suppresses duplicates, persists credit and rolls back a failed save. An active item restored without credit may earn it when visible. Keep videos and assessment attempts on their separate triggers.
- `optional`: an event-driven compatibility type. Only `required: false` excludes an item from the percentage.

The VIEW observer checks the target and its ancestors for the `hidden` attribute, `display: none`, `content-visibility: hidden` and effective zero opacity. It checks computed visibility on the target, including inherited `visibility: hidden` or `collapse`; an explicitly visible child of a hidden ancestor can still qualify. Attribute and class changes, plus the end of visibility or opacity transitions, recheck content already in the central zone without scrolling. Already earned milestones remain earned.

Required milestones have equal weight. Navigation, optional resources, footer text and Back to top are excluded. The same completed-ID set drives overall progress, per-lesson progress, checklist state, sequential unlocking and LMS completion. The checklist links to visible targets, focuses them and highlights them. A component with a hidden target can reveal it on `course-progress:reveal-target` before focus; no lesson-specific selector is built into the manager.

Sequential unlocking is set by `completion.sequentialUnlocking`. When enabled, a lesson unlocks after all required milestones in the preceding lesson are complete; lessons with no requirements pass through. When disabled, all lesson routes are available. If no milestones are configured, Progress stays at 0%, all routes remain available and no LMS completion is sent. Direct-route guards and LMS resume decisions occur after saved state is restored. Previous lessons remain available.

This setting applies between lesson routes only. Inside an accessible lesson, no content or interaction item may depend on completion of another item for access. Opening or navigating to an item does not replace its VIEW, WATCH, SUBMIT, COMPLETE or EXPLORE evidence rule.

## State and LMS behavior

Standalone launches save course-specific state in `localStorage`. LMS launches read only the LMS attempt's `cmi.suspend_data`; stale standalone progress is never imported. Suspend data includes the versioned storage key and a fingerprint of the ordered milestone schema. A mismatch makes progress read-only and displays an error, preserving the existing LMS record. Increment the storage-key version when changing requirement meaning or order.

The SCORM 1.2 bridge discovers `window.API` or an accessible parent/opener. It probes for an active LMS session before calling `LMSInitialize`, so lesson navigation, refresh and Back/Forward can reuse that session. Fresh attempts become `incomplete`. Each progress change saves bounded suspend data and lesson location, then commits. It writes `completed` and commits immediately only when a nonempty set of required milestones is fully complete. Existing `completed` and `passed` statuses are preserved. `cmi.suspend_data` above 4,096 characters is rejected with a visible save error. Save failures roll back the new milestone in the UI and do not clear the previous LMS record. Tab hiding and same-SCO navigation save without completing or calling `LMSFinish`; actual course closure saves, sets `cmi.core.exit=suspend`, commits and finishes once. Back/Forward restoration reloads from persisted state. There are no learner-facing Exit, Finish or Reset Progress controls.

Optional UI positions must pass the same 1,800-character, 64-key validation on write and read. If UI positions would push an LMS record beyond 4,096 characters, the shell saves complete requirement evidence without those positions and shows a warning. It never trims earned milestones, video ranges, exploration children or reflection text to fit. A valid fully earned LMS record left at `incomplete` after a failed status write is reconciled only after its schema and evidence are validated; an empty or fresh attempt cannot complete this way.
New watch records also keep their video duration so unique ranges can be checked against the configured threshold during recovery. Older watch records without duration retain earned progress, but cannot trigger automatic status reconciliation from `incomplete` because the threshold cannot be independently verified.

Reflection text is stored separately in browser storage under the course and learner identity; it never enters `cmi.suspend_data`. When identity or browser storage is unavailable, an activity whose approved requirement is a valid response can use memory for the current open page, with a clear message that the text will disappear on reload or leave. Set `requireDurableStorage` on `ReflectionActivity` only when the storyboard explicitly requires a durable response; without private storage, that activity then remains incomplete. The development gallery always uses session-only memory.

The package contains one SCO, a SCORM 1.2 manifest and explicit `index.html` lesson links. `package:scorm` derives its filename, manifest identifier, title and route list from the built configuration. It rewrites assets relative to each HTML folder. The ordinary static build retains root-hosted routes.

## Build and handover

Follow the [stage rules](../README.md#build-stages). In Preview or Review, run `npm run build` and relevant verification without packaging; report the SCORM ZIP as not run for that stage. The browser verifier checks configured lessons, responsive shell, typography and progress counts. Dedicated fixtures check immediate VIEW entry, hidden and offscreen targets, reveal without scrolling, duplicate credit, interaction requirements and non-numbered/nested routes with unlocking variants in both navigation modes. In explicitly requested Release preparation, build the latest approved source, then run `npm run package:scorm` and `npm run verify:scorm`. The extracted-ZIP verifier derives package identity, routes and milestones from configuration and tests strict nested hosting with a stateful simulated LMS. Its results do not replace live Oracle/People Connect acceptance.
